# Geographic data (MF-0)

Status: **implemented on branch `mf0-geo-data`, 2026-11-05.** Data and pure
logic only. No UI shows these records yet; MF-1 will.

**How the data is checked:**
- **Verbatim quotes:** every record quotes its source, and `npm run
  verify:citations` checks each quote against the live source. The quotes
  cover the PDS coordinate lines and the Trek catalog bbox strings.
- **Exact values:** integrity rules check that positions, elevations, sols,
  dates and bboxes equal the quoted values exactly.
- **Map-layer consistency:** the ortho extents equal the existing map-layer
  extents in `trek-layers.ts`.

**The traverse file** (`src/data/geo/perseverance-traverse.json`, 94 KB) is
generated by `node scripts/fetch-traverse.mjs` from the Trek MapServer layer:
- It is simplified with Douglas–Peucker at a 0.5 m tolerance, from 20,720 to
  2,947 vertices. The maximum deviation is 0.5 m.
- It keeps the attributes `sol`, `fromRMC`, `toRMC`, `length` and `fid`.

## Coordinate conventions and their limits

All positions are `[longitude, latitude]` in degrees on Mars (IAU 2000 / Mars
2000). Each record names its convention and how that convention is known.

**Stated by the source:**
- the Gazetteer (planetocentric, +East);
- the Trek sphere products (equirectangular on the Mars 2000 sphere, where
  planetocentric and planetographic latitude coincide).

**Inferred by cross-validation:**
- **The PDS sample sites.** The source prints only "Latitude (N), Longitude
  (E), Elevation". It does not state the latitude type, datum or elevation
  reference.
- **The Trek traverse.** The service declares Mars 2000 geographic (wkid
  104905) but not the latitude type.

**The inference: planetocentric latitude, east-positive longitude,
areoid-referenced elevation.** It rests on three independent products
agreeing:

| Check | Result (2026-11-05) | Reproduce |
|---|---|---|
| PDS site → nearest point on the traverse | 2.2–2.5 m for all three sites | unit test (≤ 5 m) |
| Same check with planetographic latitude | > 5 km (it would fail) | unit test |
| PDS elevation − CTX DTM elevation at the site | Pelican Point +1.8 m, Lefroy Bay +3.6 m, Comet Geyser +3.0 m | `npm run verify:geo` (≤ 10 m) |

**This is an inference, not confirmation from complete authoritative CRS
metadata.** Research task R3 stays open until PDS documentation states the
convention.

**Other limitations:**
- **ArcGIS GeoJSON output is labelled `EPSG:4326`**, but the values are Mars
  degrees. Never reproject them with Earth parameters. The adapters
  (`toGeoJson`) must be read with the Mars projection as the data projection.
- **Traverse z values are dropped.** They are undocumented and are not
  surface elevations: they range from −3989 to +2559 m, against roughly
  −2711 to −1516 m in the DTMs.
- **Use the `length` attribute for driven distance,** never the simplified
  geometry, which is 1.1% shorter. Metres is inferred: the source geometry
  matches the attribute sum within 0.04%.
- **Three rover motion counters in the source look malformed** (for example
  `3_3758` after `37_3758`). They are kept verbatim and not used for
  ordering. Segments are ordered by sol, then FID.
- **The rover position is historical.** The traverse ends at sol 1176
  (≈ June 2024; the date is not stated by the source). The rover has moved
  on since, and we have no verified geometry for that. Never call it live or
  current.
- **PDS "Date of Coring" and the sealing sol are stored as printed.** The
  app does not convert between sols and dates.
- **Coverage is partial.** Only volume 4 of the PDS initial reports has been
  curated (three margin samples). Volumes 1–3 and 5 are MF-0b.
- **Mars 2000 sphere geometry** is used for consistency checks only, with
  sub-metre error over kilometres. It is not for navigation or route
  planning.

## Separation from the scientific model

- **Geographic records never feed the engine.** `lib/evidence` and
  `lib/decision` production code do not import `lib/geo`, `lib/mission` or
  `data/geo`, and a unit test enforces this. The 36-state engine baseline is
  byte-identical.
- **The candidate tasks are simulated future actions with no coordinates.**
  No geographic record references a task or a gap.
- **`relatedObservationIds` is a factual link, not a scientific
  relationship.** A sample site links to an observation only if that
  observation's quote, or its cited source's title, names the sample:
  - Lefroy Bay → `obs-lefroy-bay-hydrated-silica`;
  - Comet Geyser → `obs-comet-geyser-carbonate-silica`;
  - Pelican Point: none.

  The link carries no review status, because it never affects rankings.

## Mission modes (`src/lib/mission/`)

| Mode | Evidence date passed to `selectEvidenceAsOf` | Geographic features |
|---|---|---|
| **Present-day (default):** simulated astronaut mission, 2026 | The latest record date in the dataset, now **2025-05-06**. Copy: "latest verified evidence in this app's dataset … not all NASA data" | All features |
| **Historical replay (advanced)** | The chosen date, within 2019-11-11 to 2025-05-06 (default 2023-09-08) | Features whose source was public on that date. The traverse is withheld until per-sol filtering exists (MF-2) |

"2026" is a mission label, not a filter date. "Astronaut" is the user's
simulated role. Observation platforms stay rover, orbital and laboratory.

## Commands

```bash
node scripts/fetch-traverse.mjs
```

```bash
npm run verify:geo
```

```bash
npm run verify:citations
```

The first regenerates the traverse; the second runs the live traverse and
DTM cross-checks; the third re-verifies every quote, geographic ones
included.
